# Shared CI and Required zizmor Workflows in giskard-actions

**Status**: accepted; amended 9 November 2026 (the scan moves to a shared script, new pins are checked online, the ruleset targets every `kind=code` repository at once, admins bypass in pull request mode).

The reusable lint, format and test workflows (**Shared CI Workflows** `python-ci.yml` and `ts-ci.yml`) and the organization-required zizmor workflow (**Required Scan Workflow** `zizmor-scan.yml`) ship from `giskard-actions` under its **Umbrella Release**, next to the release notes action and the **Reusable Review Workflow**.

**Summary for managers**

- **Cost**: about one runner minute per pull request for the zizmor scan, on top of the lint and test jobs a repository already runs, and one monthly admin step to upgrade zizmor.
- **Friction**: a pull request that adds a risky workflow pattern is blocked until it is fixed or carries a reasoned inline ignore; every code repository is fixed before the gate is turned on, and a zizmor upgrade reaches every code repository at once, so it is dry-run on the dashboard first.
- **Value**: one maintained, pinned CI for Python and TypeScript repositories, and a GitHub Actions security gate that pull requests cannot switch off.

## Context

The org-wide repository baseline asks every code repository for a CI that lints, checks formatting and runs tests, and for a zizmor scan of its GitHub Actions files on every pull request. Most repositories are uv Python or npm TypeScript projects, so the same jobs would otherwise be copied, pinned and kept up to date in each of them.

An organization ruleset can require a workflow to pass ("Require workflows to pass before merging") without a caller file in the target repository. The ruleset references the workflow by repository, path and ref, and a public repository can only require a workflow stored in a public repository. A required workflow checks out the pull request's merge commit, so anything it reads or runs from the workspace is controlled by the pull request. Rulesets have no Evaluate mode outside GitHub Enterprise. Renovate only proposes SHA pin updates (`helpers:pinGitHubActionDigests`) for repositories that publish SemVer tags.

`zizmorcore/zizmor-action` cannot be the gate. Its default collection honours `.gitignore`, so a pull request can force-add a workflow and gitignore it: zizmor skips it, GitHub runs it. It runs `python3 -m pip` with the pull request's checkout as working directory, and `-m` puts that directory first on `sys.path`, so a pull request that adds `pip/__main__.py` can fake a passing scan. It does not expose `--strict-collection`.

## Decision

- **The shared workflows live in `giskard-actions`.** It is public, so the required workflow can run on public repositories, and it publishes SemVer tags, so Renovate bumps the callers' pins. A separate repository would need its own release pipeline to get the same.
- **The baseline requires a CI, not these workflows.** A repository satisfies it with any CI that lints, checks formatting and tests; the Shared CI Workflows are the default way to do it. Every command is an input, passed through an environment variable to `bash -c` so no caller value is interpolated into a script.
- **Tool versions default to the project.** `uv-version` defaults to empty, so setup-uv installs the project's `required-version` or the latest uv; `python-version` defaults to empty, so uv reads `.python-version` or `requires-python`. `node-version` defaults to `26`, the Active LTS line, overridable.
- **Dependency caching is opt-in.** `enable-cache` (Python) defaults to `false` and `cache` (TypeScript) to empty: callers may run the workflows on release, tag or `workflow_run` events, where a poisoned cache restored from the default branch would run with release credentials, and prebuilt wheels and tarballs re-download quickly.
- **Composite actions are deferred.** The Shared CI Workflows cover single-job uv and npm or Yarn 1 projects. pnpm, service containers such as Postgres, and matrices are not supported; repositories that need them keep their own CI for now. Composite steps that such CIs could reuse will be designed once two repositories need the same thing.
- **The scan runs zizmor itself, from the digest-pinned image.** `zizmor-scan.yml` runs `ghcr.io/zizmorcore/zizmor:<version>@sha256:<digest>` with `docker run`, the pull request checked out into `src/` and mounted read-only, the config checked out into a sibling directory, and no network. The digest fixes the scanner bytes, and nothing the pull request contains is executed or on the scanner's path. A script rather than a `docker://` step, so exit code 3 (no inputs) becomes a pass. A hash-locked `pip install` into an isolated interpreter was rejected: the hashes would live in the workflow, where Renovate cannot update them (at the time, the workflow also could not tell which `giskard-actions` commit it ran from; see the amendment below).
- **Amended: the scan is a script shared with the skill and the dashboard.** `job.workflow_repository` and `job.workflow_sha` now give the commit of the running workflow, including in a ruleset run, so the workflow checks out `scripts/zizmor/` from this repository at that commit and runs `scan.sh`. The script holds the image digest and every flag; the `gha-hardening` skill and the repo-baseline dashboard run the same script, so a local pass means a gate pass. A composite action was rejected: the workflow would have to pin it by SHA in its own repository, one release behind.
- **The scan audits everything, offline, with the pedantic persona** (superseded: the auditor persona since [ADR 0005](0005-zizmor-gate-runs-the-auditor-persona.md)). `--collect=all` ignores `.gitignore`; `--strict-collection` fails on unparsable files; `--offline` disables online audits, whose external advisories could turn every pull request red without a code change. Online audits belong to the weekly repo-baseline scan, except for new pins: when a pull request adds or changes a `uses:` line, a `zizmor-pins` job runs zizmor online with the read-only job token and fails only on an impostor commit on an added line, or when zizmor cannot finish; other online findings are warnings. Pedantic is the standard every repository's own zizmor check already used, and it only added informational findings across the 10 repositories that ran zizmor. It runs on `ubuntu-latest`, which has Docker.
- **Exceptions are inline ignores, flagged for review.** An exception is a `# zizmor: ignore[<rule>] -- <reason>` comment on the flagged line, reviewed in the pull request that adds it. The scan compares ignore comments with the base commit and annotates each new one, without failing. The real control against a malicious pull request is review; the scan's job is to make risky lines visible. `--no-ignores` was rejected: it also drops the config's `ignore:` entries, which leaves only rule-wide `disable`, so one justified line switched a rule off for the whole repository. Repository-wide policy stays in the config, read from the base commit on pull requests and merge groups, so a pull request cannot loosen it for itself.
- **Only the ruleset rule is the gate.** "Require workflows to pass before merging" pins the repository, path and SHA of the workflow that must pass. A required status check matched by the name `zizmor` is not used: a pull request can satisfy it with a job of the same name in a workflow it adds or edits.
- **Fix first, then gate every code repository.** The repo-baseline dashboard first reports which repositories would fail; each is fixed (or archived). Then the ruleset targets all `kind=code` repositories at once, on the default branch, with "Do not enforce on create". A per-repository `zizmor-gate` property was dropped: one more setting to keep in sync, and a way for a repository to stay out indefinitely. The ruleset is defined in repo-baseline and applied by admins.
- **Versions move forward only.** Callers pin a release SHA and Renovate proposes the next one. A bad release is fixed forward with a patch release, never by moving or deleting a tag; a caller can stay on, or go back to, the previous SHA meanwhile. The ruleset pins `zizmor-scan.yml` by SHA; its JSON lives in repo-baseline as code (repo-baseline ADR 0001), so bumping or rolling it back is a reviewed pull request there, which Renovate can propose, applied by an admin.

## Consequences

- A `feat:` change to any shared workflow cuts a minor release that Renovate proposes to every caller; changes to `zizmor-scan.yml` also need a reviewed repo-baseline pull request that moves the ruleset SHA.
- zizmor upgrades are one monthly admin step: approve the Renovate update, release, dry-run the new version in the repo-baseline dashboard, then bump the ruleset SHA.
- In an emergency (the gate itself is broken), an organization admin merges through the ruleset's only bypass, in pull request mode; nobody can push around it. Disabling the ruleset is the last resort. Gated repositories drop any direct `workflow_call` of the scan, which would otherwise run twice.
- The ruleset does not allow `cancel-in-progress` in a required workflow, so runs of one pull request queue.
- The job fails on symlinked YAML files and on symlinks in `.github`: the runner follows them, but zizmor audits the target under its own name or skips it when it lies outside the checkout. In Actions, it also fails when a YAML file's checkout differs from its committed bytes (`.gitattributes` conversions), since GitHub runs the committed bytes.
- Before checking out its scripts, each job checks that `job.workflow_repository` is `Giskard-AI/giskard-actions` and `job.workflow_sha` a full SHA: with empty values, checkout would fall back to the pull request and run its scripts.
- `zizmor-pins` cannot check references to other private repositories of the organization (the job token reads only its own repository); it warns and skips them. Its online calls spend the repository's hourly `GITHUB_TOKEN` quota.
- Known gap: an existing ignore comment keeps covering its line when a pull request changes the code it covers (a `run:` block under an ignored line, for example); only new ignore comments are flagged. Reviewers see the change in the diff.
- Files zizmor cannot parse (test fixtures, Jinja or copier templates) fail strict collection and cannot be excepted; the dashboard dry run surfaces them before a repository is gated.
- The check shows as `zizmor` in the ruleset run and as `<caller job> / zizmor` when called as a reusable workflow. Keep the job name stable so callers' checks keep their names.
- Every pull request in a gated repository pulls the zizmor image from GHCR. The only action the scan uses is `actions/checkout`, so it is the only entry the organization actions allowlist needs; `docker run` in a script is not covered by that allowlist.
- GHCR publishes no release timestamps, so Renovate's 7-day cooldown cannot apply to the image: zizmor updates (version and digest, through a regex manager) wait for Dependency Dashboard approval, given once the same version has been on PyPI for 7 days.
- A pull request can add its own exception. It shows as a warning on the line and in the job summary, so reviewers must check its reason; the repo-baseline dashboard lists every ignore comment per repository.
- A caller that runs the scan from `pull_request_target` scans the base branch and gets false assurance; the docs forbid it.
- This repository runs `zizmor-scan.yml` on its own pull requests next to its online `zizmor.yml` (auditor persona since ADR 0005), whose job is named `zizmor-online` so only the shared scan emits `zizmor`, and which uses the same image with `--no-config`; it only adds the online audits.
